# コーディング規約（暫定）

この文書は競技プログラミング用ライブラリの現在の設計方針を記録するものです。
今後の実装・検証に合わせて継続的に更新します。コードと矛盾する場合は実装を確認し、必要に応じて文書を修正してください。

## 入出力の設計方針

### 基本方針

- 入出力の共通処理は [`utility/io.hpp`](../utility/io.hpp) に集約する。
- `io.hpp` は `io_impl::Printer` / `io_impl::Reader` と、対応するグローバルの `operator<<` / `operator>>` を提供する。
- 各ライブラリの独自型を出力可能にする場合は、原則として独自の `operator<<` を追加せず、`io_via_val` タグと `val()` を用いる。
- 入力側は同じ仕組みで一律に処理するわけではない。現在の `Reader` が対応する型、または `operator>>` を利用できる型に限る。

### include 順序

[`template/template.cpp`](../template/template.cpp) では、標準ライブラリと ACL をインクルードした後、他の自作ライブラリより先に `utility/io.hpp` をインクルードする。

```cpp
#include <bits/stdc++.h>
#include <atcoder/all>

using namespace atcoder;
#include "utility/io.hpp"

// 以降、他の自作ライブラリを読み込む
```

上記は入出力に関係する部分だけを抜粋した例です。実際のテンプレートには ACL のデバッグ用マクロなどもあります。

この順序には **C++ の二段階名前探索**への対策という目的があります。
関数テンプレート内の依存する演算子呼び出しでは、定義時点で見える宣言と、実引数依存の名前探索（ADL）によって見つかる宣言が重要です。テンプレートより後にグローバルな `operator<<` を宣言しても、それが必ず探索されるわけではありません。

この include 順序は `io.hpp` より後に定義された任意の演算子を見つけられるようにするものではありません。また、`io.hpp` より前に定義されたテンプレートの名前探索を遡って変更するものでもありません。

### 独自型の出力：`io_via_val`

出力表現を持つ自作型には、次のインターフェースを原則として提供します。

```cpp
struct Example {
  using io_via_val = void;

  long long value;

  long long val() const { return value; }
};
```

`io.hpp` 側では、`type_check::IOByVal<T>` を満たす型を検出して `Printer::print(val.val())` へ委譲します。現在の `IOByVal` はタグと `val()` を持つ型に加え、ACL の modint も対象にしています。

`val()` は **出力専用関数である必要はありません**。アルゴリズム上の値を利用者に公開する通常の API としても利用できます。ただし、戻り値は `Printer` が出力可能な型にしてください。

この方式の利点は、後から定義する自作型に対してグローバルな `operator<<` のオーバーロードを追加せずに済むことと、通常出力・デバッグ出力で共通の値表現を利用しやすいことです。

### 注意点と例外

- `io_via_val` は現在 **出力**のための仕組みです。`operator>>` の自動生成や `val()` を通した入力は行いません。
- 既存の `Printer` が直接対応するコンテナ・タプル・ACL 型などには、独自のタグを付ける必要はありません。
- `val()` が返す型の出力にも `Printer` の制約が適用されます。すべての型が無条件に出力できるわけではありません。
- 既存の独立した出力要件や外部ライブラリとの互換性がある場合、独自 `operator<<` を禁止するものではありません。ただし宣言順序と ADL を意識してください。
- 自作ライブラリは、それ自体の型・アルゴリズム定義に必要なヘッダーを明示的にインクルードします。一方、通常の利用では `io.hpp` を競技用テンプレートから先に読み込む設計とします。
