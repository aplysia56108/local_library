# コーディング規約（暫定）

この文書は競技プログラミング用ライブラリの現在の設計方針を記録するものです。
今後の実装・検証に合わせて継続的に更新します。コードと矛盾する場合は実装を確認し、必要に応じて文書を修正してください。

## 入出力の設計方針

### 基本方針

- 入出力の共通処理は [`utility/io.hpp`](../utility/io.hpp) に集約する。
- `io.hpp` は `io_impl::Printer` / `io_impl::Reader` と、対応するグローバルの `operator<<` / `operator>>` を提供する。
- 各ライブラリの独自型を出力可能にする場合は、原則として独自の `operator<<` を追加せず、`io_via_val` タグと `val()` を用いる。
- 入力側は同じ仕組みで一律に処理するわけではない。現在の `Reader` が対応する型、または `operator>>` を利用できる型に限る。

### include 順序

[`template/template.cpp`](../template/template.cpp) では、標準ライブラリと ACL をインクルードした後、他の自作ライブラリより先に `utility/io.hpp` をインクルードする。

```cpp
#include <bits/stdc++.h>
#include <atcoder/all>

using namespace atcoder;
#include "utility/io.hpp"

// 以降、他の自作ライブラリを読み込む
```

上記は入出力に関係する部分だけを抜粋した例です。実際のテンプレートには ACL のデバッグ用マクロなどもあります。

この順序には **C++ の二段階名前探索**への対策という目的があります。
関数テンプレート内の依存する演算子呼び出しでは、定義時点で見える宣言と、実引数依存の名前探索（ADL）によって見つかる宣言が重要です。テンプレートより後にグローバルな `operator<<` を宣言しても、それが必ず探索されるわけではありません。

この include 順序は `io.hpp` より後に定義された任意の演算子を見つけられるようにするものではありません。また、`io.hpp` より前に定義されたテンプレートの名前探索を遡って変更するものでもありません。

### 独自型の出力：`io_via_val`

出力表現を持つ自作型には、次のインターフェースを原則として提供します。

```cpp
struct Example {
  using io_via_val = void;

  long long value;

  long long val() const { return value; }
};
```

`io.hpp` 側では、`type_check::IOByVal<T>` を満たす型を検出して `Printer::print(val.val())` へ委譲します。現在の `IOByVal` はタグと `val()` を持つ型に加え、ACL の modint も対象にしています。

`val()` は **出力専用関数である必要はありません**。アルゴリズム上の値を利用者に公開する通常の API としても利用できます。ただし、戻り値は `Printer` が出力可能な型にしてください。

この方式の利点は、後から定義する自作型に対してグローバルな `operator<<` のオーバーロードを追加せずに済むことと、通常出力・デバッグ出力で共通の値表現を利用しやすいことです。

### 注意点と例外

- `io_via_val` は現在 **出力**のための仕組みです。`operator>>` の自動生成や `val()` を通した入力は行いません。
- 既存の `Printer` が直接対応するコンテナ・タプル・ACL 型などには、独自のタグを付ける必要はありません。
- `val()` が返す型の出力にも `Printer` の制約が適用されます。すべての型が無条件に出力できるわけではありません。
- 既存の独立した出力要件や外部ライブラリとの互換性がある場合、独自 `operator<<` を禁止するものではありません。ただし宣言順序と ADL を意識してください。
- 自作ライブラリは、それ自体の型・アルゴリズム定義に必要なヘッダーを明示的にインクルードします。一方、通常の利用では `io.hpp` を競技用テンプレートから先に読み込む設計とします。

## 整数型の扱い

### 公開インターフェース

- 自作ライブラリの公開 API では、整数を表す型として原則 `long long` を使用する。
- 競技用テンプレートでは `#define int long long` を使用するため、ライブラリの公開宣言に `int` を露出させない。呼び出し側でマクロ展開されても型・宣言が壊れないことを重視する。
- ただし、サイズ・添字・イテレータの差など、標準ライブラリとの整合が重要な箇所では `std::size_t` / `std::ptrdiff_t` など適切な型を使う。ここでの「公開整数は `long long`」は、これらを無条件に置き換える規則ではない。

### 内部実装

- 内部の局所変数・カウンタ・添字では、値域や用途が明確な場合に `int` などの小さい型を使ってよい。
- ただし `#define int long long` が有効な環境からヘッダーをインクルードする可能性を考慮し、マクロ影響を受ける `int` の利用には注意する。通常はライブラリをこのマクロの定義より先にインクルードする。
- 狭い型への変換は値域と符号に注意する。オーバーフローを回避する必要がある場合は、`long long` や `__int128` などを用途に合わせて選ぶ。

## テストと Verify の方針

### 役割分担

- `test/` は **軽量な単体・結合テスト**とする。公開 API の挙動、境界条件、例外的な構造状態、戻り値、const・型制約などを検証する。
- `components/test/` では B+tree などの内部コンポーネントを個別に検証する。必要なら private な状態や内部不変条件も直接検査してよい。
- `verify/` は実際の競技問題による正しさの確認を担い、重い乱択テスト、ストレステスト、性能評価などもこちらで扱う。テストの速さと網羅性を両立するため、重い処理を通常の `test/` に持ち込まない。
- テスト用コードはアルゴリズム本体の仕様に合わせて更新する。特定の実装詳細の偶然の挙動を、意図せず公開契約として固定しない。

### テストの書き方

- 公開インターフェースを一通りカバーし、空・1 要素・境界位置・分割／結合など、そのデータ構造特有のケースを重点的に確認する。
- 必要に応じて標準ライブラリなどの単純な参照実装と結果を比較する。乱択を使う場合も `test/` では小規模・再現可能・短時間で終わるものにする。
- 機能ごとにテスト関数を分け、各関数の末尾で `std::cerr << "○○ tests all passed!\n";` のように成功を報告する。
- `main()` の末尾にも、全テストが通過したことを示すメッセージを出力する。
- 失敗は `assert` 等で検出し、CI で非ゼロ終了として検出できるようにする。
- 実装変更に伴う回帰テストは、まず関連する最小のテストに追加する。

### CI と Verify の実行範囲

- 現在の [Linux tests ワークフロー](../.github/workflows/linux-tests.yml) は `workflow_dispatch` による手動実行で、`*/test/*.cpp` と `*/debug_test/*.cpp` を探索し、GCC（C++23）でコンパイル・実行する。ジェネレータは除外する。
- CI のテストが成功しても、`verify/` の問題群が自動的にすべて検証されたことにはならない。変更内容に応じて関連 Verify を別途実行する。
- 性能が重要な変更は、問題に即したベンチマークで比較し、単体テストに重い計測処理を組み込まない。

## ルールの更新とドキュメント化

- 新たな設計・コーディング規約を合意した際は、後から参照できるように記録する。
- **外部の読者がコードの使い方・公開 API・設計上の制約を理解するために必要な規約**は、この文書（または関連ドキュメント）への変更を PR として提案する。
- 個人のエディタ操作、実装途中の補助的な手順など、外部の利用者に不要な規約まで機械的に文書化する必要はない。
- ドキュメントの更新は原則として直接 `main` に書き込まず、レビュー可能な PR で行う。
